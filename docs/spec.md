# pagestage 首版规格

> 根据 2026-10-22 至 10-23 的设计讨论整理。术语以 [GLOSSARY.md](../GLOSSARY.md) 为准，关键决策见 [docs/adr/](adr/)。

## Problem Statement

想「听」小说的读者，手里往往是自己攒下的 TXT 网文或 EPUB。用手机自带的朗读去听，从头到尾只有一个声音：分不清是谁在说话，也没有情绪，听久了很容易走神。真人演播的多人有声书只覆盖少数热门作品。AI 多角色朗读目前只存在于封闭平台：番茄的「AI 多人有声剧」只服务自家书库，ElevenLabs 的 Character Casting 是按额度收费的创作工具，不是阅读器。开源方案大多是把整本书转成音频文件的命令行工具，需要本地 GPU，也做不到边听边看。

## Solution

pagestage 是一款以听为主、文字跟读的小说阅读器，支持 Android 和 iOS。读者导入自己的 TXT 或 EPUB，填入自己的 LLM 和 TTS key。App 先为书建档，整理出角色并推荐一份演员表；读者可以试听、换音色，也可以给主角设计专属的声音。收听时，LLM 逐章导演，决定每条台词由谁来念、带什么情绪；App 按剧本合成并播放，正文跟随高亮。App 会在收听时自动为后面几章导演和合成，播放不断档。还没有 key 的读者，可以先用内置的示例书完整体验一遍。

## User Stories

### 导入与书库

1. 作为读者，我想要从手机里导入 TXT 文件，以便听我手里已有的网文。
2. 作为读者，我想要 GBK 或 GB18030 编码的 TXT 导入后不出现乱码，以便直接使用从各处得来的文件。
3. 作为读者，我想要导入无 DRM 的 EPUB，以便听正式出版的电子书。
4. 作为读者，我想要 App 按目录或标题行自动划分章节，以便按章收听和跳转。
5. 作为读者，我想要识别不出标题行的 TXT 也能被切成章节，以便照常收听。
6. 作为读者，我想要导入同一本书的新版文件时，它被合并进原来那本书，并提示新增了几章，以便追更时不丢失已有的剧本和音频。
7. 作为读者，我想要在书架上看到导入过的书和各自的进度，以便接着听。
8. 作为读者，我想要删除一本书时，它的剧本和音频一并删除，以便释放空间。
9. 作为读者，我想要在设置里看到每本书占用的空间，并能手动清理音频，以便管理手机存储。
10. 作为读者，我想要中文书和英文书都能被正确地建档、导演和合成，以便听不同语言的书。

### 服务商与 key

11. 作为读者，我想要填入 LLM 的 base URL、key 和模型名，以便使用我自己选择的厂商。
12. 作为读者，我想要选择 LLM 走 Chat Completions 还是 Responses 接口，以便兼容不同的厂商。
13. 作为读者，我想要给建档和导演分别指定模型，以便建档用便宜的模型、导演用质量更好的模型。
14. 作为读者，我想要填入 MiniMax 和阿里百炼的 key，以便用它们合成声音。
15. 作为读者，我想要 key 只存在手机的安全存储里，以便放心填写。
16. 作为读者，我想要第一次把书的正文发给某家服务商之前，看到会发送什么、发给谁，并由我确认，以便清楚自己的数据去了哪里。
17. 作为读者，我想要服务商报错时（key 无效、余额不足、被限流）得到明确的提示，相关任务随之暂停，以便我去处理。

### 示例书

18. 作为新用户，我想要不填任何 key 就能完整体验一本示例书，以便先判断这个 App 值不值得配置。

### 建档

19. 作为读者，我想要自己决定什么时候建档，以便控制花费。
20. 作为读者，我想要只为前若干章建档，以便先试听一本很长的书。
21. 作为读者，我想要之后把建档范围往后延伸，以便继续听连载的新章节。
22. 作为读者，我想要延伸建档时，已有角色的身份和音色保持不变，以便前后的听感一致。
23. 作为读者，我想要延伸建档能认出之前出现过的同一个人，包括揭晓前的身份，以便演员表里不出现重复的角色。
24. 作为读者，我想要在 App 里看到建档的进度，并且中断后能从断点继续，以便长书不必从头再来。

### 选角与音色

25. 作为读者，我想要建档完成后自动得到一份推荐选角，以便马上就能开始听。
26. 作为读者，我想要在演员表里看到所有说话人的名字，并能直接试听各自的音色，以便知道谁会用什么声音。
27. 作为读者，我想要角色档案默认收起、点开才能看到，以便自己决定要不要冒剧透的风险。
28. 作为读者，我想要单看演员表看不出身份和角色之间的关系，以便列表本身不剧透。
29. 作为读者，我想要给某个说话人换一个预设音色，以便声音更贴合我心中的形象。
30. 作为读者，我想要按角色档案为主要角色设计新音色，试听几个候选后选定一个，以便主角的声音独一无二。
31. 作为读者，我想要台词最多的主要角色各自有专属音色，以便一听就知道是谁在说话。
32. 作为读者，我想要调整拥有专属音色的角色数量，以便在辨识度和音色资源之间取舍。
33. 作为读者，我想要群演从群演池里按性别和年龄分到合适的声音，并且同一章里开口的群演尽量不撞声，以便次要角色也听得清。
34. 作为读者，我想要每个音色可以分别使用 MiniMax 或阿里百炼，以便旁白用便宜的服务、主要角色用效果更好的服务。
35. 作为读者，我想要换掉某个说话人的音色后，只有他的台词会重新合成，以便不浪费已经生成的音频。
36. 作为读者，我想要某家服务商上的音色失效后，能按原来的声音描述重建，以便不必从头选角。

### 导演

37. 作为读者，我想要选择任意已建档的章节去导演，以便提前准备想听的部分。
38. 作为读者，我想要听到的永远是原文，一个字都不会被改写或漏掉，以便忠于原著。
39. 作为读者，我想要第三人称的叙述由旁白来念，以便叙述和对白分得清。
40. 作为读者，我想要第一人称的叙述由「我」这个角色的声音来念，以便符合第一人称小说的听感。
41. 作为读者，我想要书信、日记和系统提示由对应的角色来念，以便网文里的「系统」也有自己的声音。
42. 作为读者，我想要每条台词带上合适而克制的情绪，以便演绎自然、不浮夸。
43. 作为读者，我想要身份在揭晓之前用自己的音色，以便不被声音剧透。
44. 作为读者，我想要揭晓之后，身份的台词改用所属角色的音色；所属角色之前没出场过时，就沿用身份的音色，以便听感合理。
45. 作为读者，我想要作者的话、请假条、求票和广告这些非正文被跳过，以便听书不被打断。
46. 作为读者，我想要人名、地名、功法名里的多音字被读对，以便不出戏。
47. 作为读者，我想要导演时遇到的陌生说话人也有声音，并在下次延伸建档时被自动归入演员表，以便不需要我手动处理。

### 合成与提前量

48. 作为读者，我想要收听时 App 自动为后面几章导演和合成，以便播放不断档。
49. 作为读者，我想要分别设置导演和合成的提前量，以便控制自动生成的范围。
50. 作为读者，我想要静默阅读时不触发自动生成，以便不会意外花钱。
51. 作为读者，我想要播放到还没合成的章节时，可以选择生成本章或者用系统朗读，以便自己决定要不要花钱。
52. 作为读者，我想要把这个询问改成自动生成，以便收听不被打断。
53. 作为读者，我想要下一章还在合成时看到缓冲状态，而不是突然切换成系统朗读，以便听感连贯。
54. 作为读者，我想要合成过的音频一直保留，以便重听时不用再花钱。

### 收听与阅读

55. 作为读者，我想要在有声书模式和广播剧模式之间切换，以便选择要不要听到「他说道」这类说话提示。
56. 作为读者，我想要播放、暂停、上一句、下一句、上一章、下一章，以便控制收听。
57. 作为读者，我想要 0.5 到 3 倍速播放，以便按自己的节奏听。
58. 作为读者，我想要定时关闭，可以按时长或者播完本章，以便睡前收听。
59. 作为读者，我想要锁屏后继续播放，并能在锁屏和通知栏控制，以便不用一直开着屏幕。
60. 作为读者，我想要正文跟随播放并高亮当前台词，以便边听边看。
61. 作为读者，我想要点一下台词只会弹出操作菜单，不会直接改变播放位置，以便误触不会打乱进度。
62. 作为读者，我想要在操作菜单里选择「从这里播放」，以便跳到想听的位置。
63. 作为读者，我想要每本书都记住播放位置，精确到台词，以便下次接着听。
64. 作为读者，我想要调整字号、行距和夜间模式，以便读得舒服。
65. 作为读者，我想要播放器旁常驻「AI 合成」标识，以便清楚这是合成的声音。
66. 作为读者，我想要使用简体中文或英文界面，以便看懂 App。

### 问题反馈

67. 作为读者，我想要一键导出诊断信息，其中不含 key 和书的正文，以便放心地附到 GitHub Issue 上。
68. 作为读者，我想要从 App 里直接打开 GitHub 的新建 Issue 页面，以便方便地反馈问题。
69. 作为读者，我想要 App 不在后台上报任何数据，以便保护隐私。

### 开发者

70. 作为开发者，我想要在电脑上用 CLI 跑通建档、选角、导演和合成的全过程，以便在写 App 之前验证效果。
71. 作为开发者，我想要 CLI 输出每一步的耗时、用量（token 数、合成字数）和每条台词的说话人，以便和人工标注对照，写成原型报告。

## Implementation Decisions

### 架构

- 代码分成两个包：纯 Dart 的 core 包和 Flutter 的 app 包，用 Dart 原生的 pub workspace 管理，不引入 melos。core 不依赖 Flutter，并自带一个 CLI；原型、评测和批量调试都通过 CLI 调用 core。
- core 由下面几个深模块组成：接口小，复杂度都藏在实现里。app 和 CLI 直接调用这些模块，不再包一层只做转发的门面。
- 平台能力通过接缝（Seam）注入：密钥读取在 app 里走安全存储，在 CLI 里读环境变量或本地配置文件；数据库文件的位置也由调用方提供。播放、系统朗读、锁屏控制只存在于 app 包。
- 没有自己的服务器（ADR-0002），所有 LLM 和 TTS 请求都从设备直接发往服务商。

### 书库（Library）

- 接口：交给它一个文件，返回一本新书，或者一次更新导入的结果（新增了几章、哪些章节的正文变了）。
- TXT：先按严格 UTF-8 解码，失败再按 GB18030 解码（GBK 是它的子集）。章节按标题行识别，例如「第X章」「第X回」「Chapter X」；识别不出来就按约 5000 字切分。「卷」只用于分组。
- EPUB：只处理无 DRM 的文件。章节以目录为准：一个文件里有多章就拆开，一章跨了多个文件就合并；没有目录时才按文件划分。只提取正文和目录，不保留样式。
- 导入时按内容识别书的语言（中文或英文），后续的提示词和 TTS 都按这个语言选择。
- 更新导入：新文件开头 3 章的正文和书架上某本书一致，就当作这本书的新版本。正文没变的章节保留剧本和音频；正文变了的章节，剧本和音频作废；新章节接在后面；建档范围不变。

### 建档（Profiler）

- 接口：给它一本书和目标章节，它把建档范围延伸到这一章，返回更新后的演员表和发音词典，过程中报告进度。
- 按章节分批调用建档模型，每完成一批就保存结果，因此可以断点续跑。
- 每次调用的提示词都带上已有的角色、别名、身份和临时角色，帮助 LLM 认出同一个人，包括揭晓前的身份，避免建出重复的角色。
- 输出包括：
  - 角色：别名、性别、年龄、性格、说话方式、声音描述、台词量、出场章节；
  - 身份：所属角色、揭晓章节；
  - 临时角色的去向：合并进已有角色、转为正式角色，或继续保持临时；
  - 发音词典：中文专有名词里的多音字及其拼音。
- 已有的角色、身份以及它们的音色都不变。重复的条目自动合并，保留台词更多那一方的音色。

### 选角与音色（Casting）

- 接口：给它一本书，返回演员表中每个说话人的音色；另外提供试音（为一个说话人生成候选音色并选定其一）和换音色两个操作。
- 推荐选角：
  - 按台词量排序，前 20 个角色各自独占一个预设音色，这个数量可以调整。
  - 其余角色和临时角色都是群演，从群演池里按性别和年龄段（儿童、少年、青年、中年、老年）分配音色。
  - 分配池音色时参考建档记录的出场章节，尽量让同一章里开口的群演不共用一个音色。导演时新出现的临时角色，在合成前按同样的规则补分配。
  - 旁白的音色按书的语言推荐。
- 音色由声音描述和样音组成；音色绑定记录服务商、模型和服务商一侧的音色参数（ADR-0003）。每个音色可以单独绑定 MiniMax 或阿里百炼。
- 音色设计：在支持的服务商上（MiniMax，以及阿里百炼的北京区）按声音描述生成几个候选，由用户试听后选定。选定后立刻用它合成一次样音，避免 MiniMax 设计出的音色在 7 天后过期。
- 音色绑定失效时（例如服务商下线了某个音色），按声音描述重建，并提示用户重新试听。
- 换了音色之后，这个说话人已经合成的音频作废。

### 导演（Director）

- 接口：给它一个已建档的章节，返回这一章的剧本。
- 提示词包含三部分：截至这一章读者已知的演员表（揭晓之前，身份只以身份本身出现）、上一章结尾的几条台词，以及本章原文。
- 由 LLM 划分台词，每条台词都带上原文和表演指令（ADR-0004）。表演指令包括：
  - 说话人；
  - 情绪：平静、开心、悲伤、愤怒、恐惧、厌恶、惊讶，七选一；
  - 强度：轻、中、强三档；
  - 一句表演说明；
  - 是否是说话提示；
  - 是否是非正文。
- 叙述的指派：第三人称叙述归旁白，第一人称叙述归「我」这个角色，书信、日记和系统提示归对应的角色。
- 提示词要求克制：只有情绪明显时，才标平静以外的情绪。
- 使用结构化输出（JSON）。太长的章节按自然段分块导演，每块带上前一块结尾的几条台词作为上下文；分块的阈值由原型决定。
- 对齐：导演完成后，把每条台词对齐回原文，得到它在原文中的区间。标点、空白和全角半角的差异都在容差之内。朗读和高亮一律使用对齐后的原文。
- 对不上的处理：有原文没被任何台词覆盖，或者有台词在原文里找不到时，重新导演，最多 2 次。仍然对不上的话，没覆盖到的原文补成由旁白念的台词，找不到的台词丢弃。整个过程用户看不到。
- 遇到演员表里没有的说话人，就建一个临时角色。
- 每份剧本都记录生成它所用的模型和提示词版本。

### 合成（Synthesizer）

- 接口：给它一章的剧本，产出每条台词的音频。只有导演过的章节才能合成。
- 合成请求携带原文、语言、音色绑定、表演指令和适用的发音词典条目。适配器负责将表演指令转换为厂商参数：MiniMax 使用情绪枚举；阿里百炼将情绪、强度和说明组合成一句自然语言指令。
- 发音词典只对中文生效：MiniMax 通过发音词典参数传入，阿里百炼用 SSML 的拼音标注。
- 音频按原文、语言、音色绑定、表演指令、适用的发音词典条目和合成策略版本缓存；适配器的参数映射发生变化时更新策略版本。
- 不同服务商合成的音频要统一响度。
- 相邻的旁白台词要不要合并成一个请求来提升连贯性，看原型的听感结论再定。

### 调度（Scheduler）

- 接口：告诉它当前的收听位置，以及用户发起的操作（建档、导演或合成某些章节），由它负责排队执行并报告进度。
- 建档、导演、合成都是持久化的任务，按章节记录进度；App 回到前台或重新打开后，从断点继续。进度只在 App 内显示，不做后台保活；等原型测出建档耗时后再重新评估。
- 提前量：
  - 只在收听时生效。收听第 N 章时，确保第 N+1 章到第 N+导演提前量 章已经导演，第 N+1 章到第 N+合成提前量 章已经合成；已经完成的章节跳过。
  - 默认导演提前 2 章、合成提前 1 章。合成的提前量不能超过导演的提前量；设为 0 即关闭自动生成。
- 播放到还没合成的章节时，默认询问用户：「生成本章」还是「用系统朗读」，不显示金额。设置里可以改成自动生成。如果下一章正在合成，就显示缓冲状态，等它完成。
- 服务商报错（key 无效、余额不足、被限流）时，暂停相关任务并在 App 内提示，不自动切换服务商。

### 服务商适配器

- LLM：一个兼容 OpenAI 通用接口的适配器，支持 Chat Completions 和 Responses 两种调用方式，需要配置 base URL、key 和模型名。建档模型和导演模型各占一个槽位，默认相同。用哪家厂商由用户自己选。
- TTS：MiniMax 和阿里百炼各有一个适配器，按所选模型和音色声明是否支持拼音标注及单次请求的字数上限，并负责合成、厂商参数转换、响应解析和错误码归类。支持音色设计的适配器实现独立的设计接口，在发送请求前校验模型、地域、endpoint 和请求内容。HTTP 状态分类和异常脱敏由共享模块处理。接入新的服务商时新增相应适配器。
- key 永远不写进日志。

### App

- 包括书架、章节目录和滚动式正文；可以调字号、行距，有夜间模式；界面提供简体中文和英文。
- 播放器：
  - 播放/暂停，上一句/下一句，上一章/下一章；
  - 0.5 到 3 倍速；
  - 定时关闭，按时长或播完本章；
  - 后台播放，锁屏和通知栏控制。
- 正文跟随播放，高亮当前台词。点一下台词会弹出操作菜单，首版菜单里只有「从这里播放」一项；点击本身不改变播放位置。
- 每本书记住播放位置，精确到台词。
- 演播模式按书设置，默认有声书模式。非正文在两种模式下都跳过。
- 演员表列出全部说话人，身份和它所属的角色各占一行。每一行显示名字和试听按钮；查看档案、换音色、音色设计都放在二级菜单里。
- 系统朗读用手机自带的 TTS，以单一声音念原文。
- 播放引擎用 just_audio 还是 flutter_soloud，在 App 阶段的第一个 Flutter 原型里决定。后台播放和锁屏控制用 audio_service。

### 存储

- 用 drift（SQLite）保存书、章节、演员表、音色、剧本、任务和播放位置；音频文件存放在本地。
- 合成出来的音频一直保留，直到删除这本书或者在设置里手动清理。设置里显示每本书占用的空间。
- 不做跨设备同步，也不做备份。

### 合规与隐私

- 第一次把书的正文发给某家服务商（LLM 或 TTS）之前，先弹窗说明会发送什么、发给谁，用户同意后才发送。同意状态按服务商分别记录。
- 播放器旁常驻「AI 合成」标识。
- 内置一本示例书：取一部公版作品的前几章，剧本和音频都预先生成好，随 App 一起打包，不需要 key。
- 上架 Google Play 时，加一个应用内举报 AI 内容的入口：在 App 内用 WebView 打开第三方表单。
- 不接入第三方统计或崩溃上报 SDK，也不自动上报任何数据：
  - Dart 层的异常写进本地日志；
  - 原生崩溃在下次启动时从系统取回，iOS 用 MetricKit，Android 用 ApplicationExitInfo；
  - 用户可以一键导出诊断信息，导出内容不含 key 和正文；
  - 「反馈问题」入口打开 GitHub 的新建 Issue 页面。

### 数据模型（概念层面）

- 书：语言、来源文件、建档范围、演播模式、提前量设置。
- 章节：顺序、标题、正文、正文哈希。
- 演员表成员：
  - 旁白；
  - 角色：别名、角色档案、台词量、出场章节；
  - 身份：所属角色、揭晓章节；
  - 临时角色。
- 音色：声音描述、样音。音色绑定：服务商、模型、服务商一侧的参数。
- 剧本：所属章节、生成所用的模型、提示词版本。
- 台词：原文区间、表演指令、是否是说话提示、是否是非正文。
- 音频：缓存键、文件、时长。
- 其他：发音词典条目，任务（类型、范围、进度、状态），服务商同意记录，播放位置。

## Testing Decisions

- 好的测试只通过模块的接口验证外部行为，不碰实现细节。比如不去断言提示词里的字符串，而是给导演模块一个预先写好的 LLM 回复，检查得到的剧本和原文区间对不对。
- 测试接缝放在服务商这一层。LLM 和 TTS 两处各自都有两个真实的适配器：LLM 是 Chat Completions 和 Responses，TTS 是 MiniMax 和阿里百炼。所以它们是真实的接缝，测试时换成假适配器即可：假 LLM 返回预先写好的回复，假 TTS 返回时长可以预测的短音频。
- 各模块的测试重点：
  - 书库：GBK 和 UTF-8 编码的 TXT、各种标题行、没有标题行的 TXT、目录和文件对不上的 EPUB、更新导入的识别与合并。
  - 建档：分批处理和断点续跑；带上已有演员表后能认出同一个人；身份和揭晓章节；临时角色的去向；合并重复条目时保留哪一方的音色。
  - 导演：对齐的各种情况，包括改了标点、漏了段落、编造了台词、全角半角不同；重试次数和最后的兜底；长章节分块；第一人称叙述和书信的指派；未知说话人变成临时角色。
  - 选角：主要角色独占音色；群演池的分配和同章避让；换音色后对应的音频作废。
  - 合成：表演指令按服务商能力的映射；发音词典的应用；缓存的命中与失效。
  - 调度：提前量只在收听时生效；合成提前量不超过导演提前量；重启后从断点继续；服务商报错时暂停。
  - 服务商适配器：用录制的 HTTP 响应做契约测试，覆盖请求格式、响应解析和错误归类（key 无效、余额不足、被限流）。
  - App：少量 widget 测试，只覆盖关键交互，比如点台词只弹出菜单、不跳转播放。
- 先例：仓库里目前还没有代码，这是第一批测试。
- 说话人准确率属于质量评测，不放进自动化测试。用 CLI 对人工标注过的章节跑评测，结果连同模型和提示词版本一起记录。公开的评测集只能使用公版或自己写的文本。

## Out of Scope

- 书源、书城和网页抓取（ADR-0001）。
- 自己的服务器、托管服务、账号体系、跨设备同步和备份（ADR-0002）。
- 桌面端和 Web 版。
- PDF、MOBI/AZW3 和带 DRM 的文件；中文和英文以外的书。
- 费用预估、预算上限和花费账本。
- 手动修改台词的说话人或情绪、手动编辑发音词典。
- 音频导出和分享。
- 分页和仿真翻页、笔记。
- 均衡器、背景音乐和音效。
- 后台保活和系统级的进度显示（等原型结果出来再议）。
- 第三方统计和崩溃上报 SDK，以及任何自动上报。
- 克隆真人的声音。
- MiniMax 和阿里百炼以外的 TTS，以及 OpenAI 通用接口以外的 LLM 接口（都留待以后扩展）。
- 发布渠道（暂不考虑）。

## Further Notes

- 第一步是 CLI 原型，预计 1 到 2 周。用《阿Q正传》（鲁迅，1921）和《傲慢与偏见》的前 5 章，两本书在全球都已进入公版，也是示例书的候选。也可以拿自己手头的网文 TXT 私下测，但不提交到仓库。原型结果写进 `docs/spike-report.md`，包括：
  - 建档的耗时和用量；
  - 说话人准确率（以人工标注作对照）；
  - 每章导演和合成的耗时和用量；
  - 逐句合成的听感，以及中英文在两家 TTS 上的效果。
- 原型不设硬性及格线，听完后由你决定是否进入 App 开发。
- 下面这些问题等原型来回答：
  - 建档需要多久，以此决定要不要做后台保活；
  - 说话人准确率和听感；
  - 导演时长章节的分块阈值；
  - 相邻的旁白台词是否合并合成；
  - 示例书最终用哪一本。
  - 播放引擎在 App 阶段的第一个 Flutter 原型里决定。
- 服务商现状（2026-10 调研）：
  - OpenAI 的 TTS 模型将于 2027-01-06 下线。
  - MiniMax 设计出的音色 7 天内不用来合成就会过期。
  - 阿里百炼的音色设计只在北京区提供。
  - 各家计费规则不同：汉字在 Azure、MiniMax 和阿里按 2 个字符计费。这也是不做费用预估的原因之一。
- 合规背景：苹果审核指南 5.1.2(i) 要求把数据发给第三方 AI 之前取得用户同意；Google Play 有 AI 生成内容政策和用户数据政策；国内有《人工智能生成合成内容标识办法》。发布渠道暂不考虑，上架前需要重新评估：App Store 中国区要办 APP 备案，国内安卓商店对 AI 功能还要求算法备案等材料。
